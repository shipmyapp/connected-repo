# Monorepo Agent Guidelines (AGENTS.md)

## 1. Blueprint
**Intent**: Production-ready full-stack TS monorepo with E2E type safety and offline-first delta sync.
**Core Stack**: 
- **Repo**: Turborepo + Yarn
- **Backend**: oRPC + Orchid ORM + PostgreSQL + Redis (rate limits) + pg-tbus + Better Auth
- **Frontend**: React 19 + Vite + TanStack Query + Dexie.js (IndexedDB) + pull-delta sync (no SSE)
- **Packages**: Shared Zod schemas, UI components (MUI)
- **Tooling**: Biome (Tabs, 100 chars, double quotes), knip

**Architecture Patterns**:
- **Bimodal Docs**: `README.md` (Human) vs `AGENTS.md` (Agent)
- **Worker Isolation**: `DataWorker` (DB/Sync) vs `MediaWorker` (Stateless/Uploads)
- **Sync Integrity**: Offline mutations allowed ONLY for unsynced records.
- **Strict TS**: NO `any`, NO `as unknown`, NO `ts-ignore`.

## Rule: Novu workflows and templates
People edit notification wording in the Novu dashboard, and code that is newer than the dashboard overwrites it at the next boot (ADR-044). So before any change to `apps/backend/src/novu/workflows/` or `apps/backend/src/novu/layouts/` (a template, a layout, a step, a payload variable, a new or removed workflow, or a trigger's `workflowId`/`payload`):
1. Check the dashboard: run `yarn workspace @connected-repo/backend novu:status --app-url <that deployment's WEBAPP_URL>` with the Novu environment's Secret Key (Production unless they say otherwise) from the session's environment variable `NOVU_SECRET_KEY`, and `NOVU_API_URL` (skill `novu-pull`, step 1). 5. Repeat the summary in the PR description.
If the key or the Novu API is unavailable, say so and say that the dashboard was not checked. Do not go ahead as if it matched.

## Rule: personal data and the legal texts
A change that collects new personal data, adds a processor or a cookie updates `docs/legal/privacy.md` and bumps `LEGAL_VERSION` (`packages/zod-schemas/src/legal.zod.ts`) in the same pull request (ADR-049). A new table that names a person gets a line in `purgeAccount` (or a CASCADE foreign key), a named column list in `exportAccountData`, and an entry in the purge test's list of person columns.

## Quick Reference
- **Dev**: `yarn dev`
- **Build**: `yarn build`
- **Deploy**: Dokploy, Compose (`docker-compose.prod.yml`) or one Application per Dockerfile (`deploy/dokploy/`); see `deploy/README.md`
- **Check**: `yarn lint`, `yarn format`, `yarn check-types`, `yarn knip`, `yarn check:deploy` (env and deploy files agree)
- **Hooks** (no dead code, as we go): `yarn install` points git at `.githooks/`. **pre-commit** runs Biome on the staged files (unused imports and variables are errors); **pre-push** runs `yarn knip` (unused files, exports, types, dependencies) and `yarn check-types`; CI runs both and lint. They are clean on `main`, so a red one is yours: remove what the change left unused (an old path a new one replaced, a helper nobody calls, a dependency) rather than exporting it again or skipping the hook. Code of a kept feature that knip cannot see is taught to `knip.jsonc` with a comment, never deleted.
- **DB**: `yarn db g <name>`, `yarn db up`, `yarn db seed`
- **Console**: http://localhost:5175 (superadmin; needs ALLOWED_ORIGINS + SUPER_ADMIN_EMAILS)
